# InspireStudio 技术架构设计文档 V1.0

**项目名称：** InspireStudio（灵感工坊）

**项目定位：** 面向所有创作者的通用多模态 AI 创意工具箱

**技术方案版本：** V1.0

**开发语言：** TypeScript + Python

---

## 一、项目总体架构

### 1.1 系统架构

采用前后端分离的模块化架构。

系统由五个主要部分组成：

1. 前端展示层：负责用户界面和交互。
2. 后端业务层：负责项目管理、数据处理和 API 接口。
3. AI 调度层：负责模型调用、Prompt 管理和任务编排。
4. 媒体处理层：负责图片、音频和视频处理。
5. 数据存储层：负责项目、素材、版本和任务记录。

### 1.2 技术选型

| 技术 | 用途 |
|---|---|
| React | 前端界面 |
| TypeScript | 前端开发语言 |
| Vite | 前端构建工具 |
| Tailwind CSS | 页面样式 |
| Tiptap | 富文本编辑器 |
| Zustand | 前端状态管理 |
| Python | 后端开发语言 |
| FastAPI | 后端接口框架 |
| SQLAlchemy | 数据库 ORM |
| SQLite | 数据库存储 |
| FFmpeg | 音视频处理 |
| Git | 版本管理 |

初期采用本地文件存储，不引入复杂的云存储系统。

### 1.3 AI 模型架构

采用模型适配器设计。

不同 AI 服务通过统一接口接入：

- LLM：文本生成、创意策划、意图识别。
- Image Model：图片生成和视觉编辑。
- TTS：文本转语音。
- ASR：语音转文字。

更换模型供应商时，尽量不修改业务层和前端代码。

## 二、系统模块设计

### 2.1 统一创意中心

- 创建和管理创意项目。
- 保存项目主题和目标受众。

1. 社交媒体文案。
2. 文章创作。
3. 广告文案。
4. 产品介绍。
5. 短视频脚本。

主要功能：

- AI 文案生成。
- 润色、改写、扩写、缩写、续写。
- 标题生成。
- 简洁编辑模式。
- 专业富文本编辑模式。
- 局部修改。
- 历史版本管理。
- TXT 导出。

### 2.3 视觉工坊

主要功能：

- 文生图。
- 参考图片辅助生成。
- 风格选择。
- 图片比例选择。
- 多候选图片生成。
- AI 海报设计。
- 封面设计。
- 图片预览和下载。
- 文字排版与可视化编辑。
- 图片版本管理。

图片生成模型负责视觉内容，前端排版引擎负责中文文字和布局。

### 2.4 音频工坊

主要功能：

- TTS 文本转语音。
- ASR 语音转文字。
- 音色选择。
- 语速调整。
- 音频试听。

### 2.5 视频工坊

| 项目 | 规格 |

| 视频时长 | 15秒、30秒、60秒 |

主要功能：

- AI 视频脚本生成。
- AI 自动分镜。
- 图片和视频素材导入。
- 配音导入。
- 字幕生成与编辑。
- 基础时间线编辑。
- FFmpeg 自动合成。
- 视频预览与导出。

### 2.6 创意资产中心

统一管理：

- 文案。
- 图片。
- 音频。
- 视频。
- 项目文件。
- 历史版本。
- Prompt 记录。

## 四、数据库设计

第一版采用 SQLite。

主要数据表：

| 数据表 | 作用 |
|---|---|
| users | 用户信息，后续扩展 |
| projects | 创意项目 |
| project_contexts | 项目创意上下文 |
| creative_tasks | 创作任务 |
| prompt_records | Prompt 记录 |
| ai_executions | AI 调用记录 |
| assets | 创意素材 |
| asset_versions | 素材版本 |
| workflows | 跨工坊工作流 |

### 核心关联关系

- 一个项目可以拥有多个创作任务。
- 一个项目可以拥有多个素材。
- 一个创作任务可以产生多个素材版本。
- 一个任务可以关联多个 Prompt 和 AI 执行记录。
- 一个视频项目可以引用文案、图片和音频素材。

所有素材通过 project_id 关联到所属项目。

### 版本管理

每次重新生成或修改素材时，创建新的版本记录。

不直接覆盖用户已经确认的旧版本。

## 六、AI 调度器设计

AI 调度器是本项目的重要技术模块。

工作流程：

1. 接收用户自然语言指令。
2. 读取当前项目上下文。
3. 识别用户意图。
4. 生成结构化任务计划。
5. 判断是否需要用户确认。
6. 调用对应工坊。
7. 保存执行记录。
8. 返回生成结果。

例如：

用户输入：

「帮我把这段文案制作成一条30秒的竖屏宣传视频。」

调度器识别：

- 任务类型：视频制作。
- 视频时长：30秒。
- 比例：9:16。
- 输入素材：当前项目文案。
- 需要调用：视频脚本、分镜、配音、视频合成。

涉及图片、语音等可能产生额外费用的任务，执行前应提供确认机制。

模型只能提出结构化任务，不能直接执行任意系统命令。

## 七、异步任务设计

图片生成、语音生成和视频合成可能耗时较长。

因此需要独立的任务管理机制。

任务状态：

- pending：等待执行。
- running：正在执行。
- succeeded：执行成功。
- failed：执行失败。
- canceled：已取消。

前端通过定时查询任务接口获取状态和进度。

第一版采用 SQLite 任务记录和独立后台 Worker，不急于引入 Redis、Celery 等复杂基础设施。

FFmpeg 视频合成在后台执行，避免阻塞前端请求。

## 八、安全与错误处理

### API 密钥安全

- API Key 只保存在后端。
- 不允许将密钥写入前端代码。
- 使用 `.env` 管理本地密钥。
- `.env` 加入 `.gitignore`。
- 提供 `.env.example` 作为配置模板。

### 文件安全

- 检查上传文件格式和大小。
- 使用随机文件名。
- 防止路径穿越。
- 限制可访问的文件目录。
- 对外提供受控下载接口。

### 错误处理

统一处理：

- 模型调用失败。
- 网络超时。
- API 配额不足。
- 图片生成失败。
- 音频处理失败。
- FFmpeg 合成失败。
- 文件上传失败。

失败任务应保留错误原因，支持必要的重新执行。

## 这份文档之后，我们还需要确定三件事

> 以下为原方案的默认假设，仍待后续确认，不视为新增的已确认决策。

当前方案包含三个技术上的默认选择：

1. **本地优先开发：** 先在 Windows 电脑运行，后续再部署到服务器。
2. **模块化单体架构：** 前后端分离，但后端先不拆成微服务，降低开发难度。
3. **模型供应商暂不锁定：** 先设计统一接口，再选择实际可用的模型 API。

特别是第三点，我们不能在没有测试模型效果、价格和 API 可用性的情况下，贸然决定供应商。
